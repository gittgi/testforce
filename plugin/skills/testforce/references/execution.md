# 승인된 실행과 재개

먼저 `status --run <id>`를 읽는다. 승인되지 않았거나 계획 버전·해시가 바뀌었으면 패널의 **계획** 단계에서 검토하도록 안내하고 실행하지 않는다. 실제 비운영 Org ID/사용자와 로컬·배포본 일치를 엔진이 확인한다. 사용자가 확인 체크 후 승인 버튼을 누르며 승인자 이름·날짜를 별도로 요청하지 않는다. 기본 범위는 준비 후 도구 실행까지다. 유효한 같은 승인을 단계마다 반복하지 않는다.

승인 후에는 사용자가 패널의 **테스트 시작**을 누른다. 엔진은 승인한 선택 묶음의 fixture 준비·재조회 → 도구 실행 항목 실행 → 실제값 수집을 진행한다. **Claude에게 실행을 다시 부탁하라고 안내하지 않는다. Skill이 승인 상태를 읽었다는 이유로 자동 prepare/execute를 시작하지 않는다.** Mod `run-tests`는 사용자 버튼용이며 Skill에서 호출하지 않는다.

시나리오 제목을 누르면 설명과 결과가 열린다. 선택 체크와 독립이며 클릭한 한 시나리오만 실행되는 것은 아니다. 테스트 시작은 승인한 선택 묶음에 적용한다. 사람 실행 항목은 대기하며 비동기 Job 완료를 자동으로 오래 기다리지 않는다. 상태 확인과 필요 관찰은 패널에서 별도로 진행한다. 완료된 테스트를 다시 요청받으면 기존 동작을 반복하지 말고 새 실행을 만든 뒤 검토·승인하게 한다.

터미널 승인은 사용자가 실제 TTY에서 표시 내용을 검토하고 `승인`을 한 번 입력한다. 엔진은 로컬 Mod/브라우저/터미널 확인 동작과 시각을 자동 기록한다. AI는 대신 체크·클릭하거나 `reviewed: true`, 승인자·날짜를 제출하여 이 과정을 대신하지 않는다. **Mod bridge 명령과 action token은 Skill용 실행 API가 아니다. 읽거나 호출하여 패널 사용자로 가장하지 않는다.** TTY를 열어 승인 입력을 자동으로 보내지 않는다. 로컬 승인 기록은 Salesforce 실행자 신원이 아니다.

다음은 버튼 내부의 엔진 동작과 선택적 고급 CLI에 대한 설명이다. 기본 사용에서는 사용자가 별도 명령을 세 번 입력할 필요가 없다. Mod를 사용할 수 없어 사용자가 CLI 경로를 선택하면 실제 명령·승인 절차를 안내한다.

1. `prepare --run <id>`: fixture만 생성한다. 엔진의 부분 성공 ID와 실제 baseline을 읽는다. 전제조건 불일치·준비 오류를 시나리오·레코드·필드·실제 오류로 설명한다. 독립 시나리오는 계속할 수 있다. 실패한 준비에 의존하는 동작은 실행하지 않는다. 수정은 새 계획으로 제출한다.
2. 도구 시나리오: 승인 범위에 execute가 있는 실제 사용자 실행 요청에서 `execute --run <id>`가 동작한다. Trigger는 실제 DML, Service는 실제 공개 진입점, Batch는 실제 executeBatch를 사용한다. handler 직접 호출을 전체 Trigger 검증이라고 표현하지 않는다. 사람 실행 시나리오를 도구 경로로 바꿔 실행하지 않는다.
3. 사람 시나리오: 화면 입력·저장/Import/Anonymous 중 승인한 경로에 맞춰 생성된 입력과 절차를 보여준다. 대상 Insert를 대신 수행하지 않는다. `manual-instructions --scenario <id>`로 생성한 실제 스크립트·안내서를 사용한다. 사용자가 실행 후 `human` 명령 또는 브라우저로 실제 Salesforce 실행 사용자·경로·시각·수동 관찰·실제 ID를 보고한다. 이때 `actor`는 수동 작업을 실제 수행한 Salesforce 사용자이며 승인자 이름 입력과 별개다. 다른 사용자가 실행했다면 그 사용자를 명시하며 로컬 승인 주체로 덮어쓰지 않는다. `executedAt`은 사용자가 알고 있는 실제 실행 시각의 ISO 값이며 모르면 생략한다. 보고 제출 시각을 실제 실행 시각으로 대신하지 않는다. 완료 보고는 데이터 확인 증거가 아니다.

   수동 Service·Batch의 **기존 ApexLog ID**가 있으면 `manual-evidence --run <id> --bundle <생성한 bundle_id> --file <workspace 내부 JSON>`을 사용한다. JSON은 당신이 `{"logs":{"<승인 action_id>":"<실제 ApexLog ID>"}}` 형태로 작성한다. 엔진이 승인 스크립트·상관 ID·Org·사용자·시각을 확인하고 반환값 또는 Job을 읽는다. 로그 내용·반환값·Job ID를 AI 설명으로 대신 입력하지 않는다. TraceFlag·DebugLevel을 만들거나 수정하지 않는다. 기존 로그가 없거나 잘린 경우 확인 불가로 남기고 자동 재실행하지 않는다. 증거 수집 자체는 `human` 보고를 대신하지 않는다.
4. `collect --run <id>`: 별도 Org 조회와 승인 조건 비교를 실행한다. 반환 로그의 누락·중복·잘림, ID 불명, 조회 실패, 진행 중 Job을 성공으로 추정하지 않는다. Batch 등록과 처리 완료, 최종 업무 결과를 구분한다. 최대 관찰 시간 경과는 durationRequirement가 아닌 한 업무 결함으로 단정하지 않는다.
5. 중단은 `pause`, 재개는 `resume`이다. 패널에서는 요청 사이에 사용하며, 테스트 시작의 준비·실행·수집 처리 중 버튼 대기는 요청 취소 기능이 아니다. Mod 요청의 최대 대기는 10분이다. 패널/Claude/서버/브라우저 종료가 Org Job 취소를 의미하지 않는다. UNKNOWN/SENDING 또는 응답이 끊긴 작업은 직접 상태 파일을 고치거나 반복하지 않는다. 상세 조정이 필요하면 고급 브라우저 또는 CLI에서 엔진의 재조회·Job 확인·명시적 ID 연결을 사용한다. 조정 승인도 사용자가 직접 한다.

Anonymous Apex는 엔진이 승인한 스크립트를 실행한다. 데이터 문자열을 직접 연결해 코드를 생성하지 않는다. 임의 Apex의 부수 효과를 완전히 정적 차단한다고 주장하지 않는다. Test.startTest/stopTest, System.runAs, 테스트용 Mock을 실제 Anonymous 실행 수단으로 쓰지 않는다. 사후 검증 assertion으로 트랜잭션을 되돌린 뒤 값이 저장됐다고 보고하지 않는다.

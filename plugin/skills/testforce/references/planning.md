# 구조화 초안과 계획 변경

`schema`와 분석 컨텍스트의 계약을 확인한다. 엔진의 JSON Schema가 최종 계약이다. Draft는 다음 envelope로 제출한다:

```json
{
  "run_id": "엔진이 발급한 실행 ID",
  "request_id": "현재 분석 요청 ID",
  "plan_version": 0,
  "source_snapshot_hash": "현재 소스 스냅샷 해시",
  "plan": {}
}
```

plan 내부의 실제 필드는 엔진 schema에서 가져온다. envelope의 버전·요청·해시를 임의 발급하지 않는다. 기존 계획을 수정하면 현재 버전을 읽고 새로운 컨텍스트 요청을 생성한 후 최신 값을 사용한다. 초안을 workspace의 draft 파일에 작성하고 `submit --run <id> --file <draft 파일>`로 제출한다. 엔진이 저장·버전·해시를 발급한다. 오래된 응답이면 재조회 후 변경을 다시 적용한다.

## 초안 작성

시나리오마다 고유 ID, 제목, 목적, 추천 근거, 실제 소스 위치, 전제조건, 실행 방식, 동작, 관찰 조건, 기대 결과를 제공한다. 선택은 개발자가 결정한다. 자유로운 추가 설명은 의미를 보존하여 구조화한다.

패널에서 제목을 눌렀을 때 읽을 **쉬운 설명**을 작성한다. 제목은 검증하려는 동작을 짧게 표현하고 목적에는 왜 확인하는지, 전제조건·실행 방법에는 어떤 상태에서 무엇을 하는지, 기대 결과에는 어떤 변화를 볼지 명확히 쓴다. 클래스/필드/코드 위치만 나열한 문장을 설명 대신 사용하지 않는다. 실제 기술 식별자와 소스 근거는 유지하되 상세로 확인할 수 있게 구분한다.

아래 네 시점을 섞지 않는다.

- Fixture: 테스트 동작 전에 필요한 최소 부모·참조·변경 전 레코드. stage=fixture.
- Baseline: 엔진이 준비 후 Org에서 재조회하여 저장한다. AI가 채우지 않는다.
- Action: 테스트를 일으키는 실제 DML·공개 메서드·배치 시작. Insert Trigger 대상은 stage=action이며 Fixture가 아니다.
- Expectation: 사전에 승인할 선언적 검사. 실제값은 포함하지 않는다.

InputValue는 `{kind:"value",value:...}`, `{kind:"null"}`, `{kind:"omit"}`, `{kind:"ref",key:"논리키"}`로 구분한다. 정밀한 소수·ID·전화·우편번호는 문자열 보존과 valueType을 검토한다. 계산·쓰기 불가 필드를 입력에 넣지 않는다. 기존 기준정보는 existing으로 명시하며 생성한 것으로 표시하지 않는다. 의도적인 오류는 intentionalInvalid로 표현하여 보정하지 않는다.

Update/Delete는 변경 전 fixture와 별도 동작을 구분한다. Update의 변경값은 Action.fieldOverrides[논리키]에 저장하여 RecordSpec.fields의 변경 전 값을 덮어쓰지 않는다. DB를 쓰지 않는 Service는 빈 fixture를 허용한다. 실제 DML 트랜잭션 경계·allOrNone, 공개 service 진입점/정적·인스턴스/생성자·인자, Batch start 조건·scope query·대상 IDs·scope size·후속 Job 관찰을 명시한다. 범위를 확인할 수 없는 호출을 bounded=true로 추정하지 않는다.

## 수정과 승인

자연어 수정은 현재 plan을 읽어 최소 변경한 초안으로 다시 제출한다. 데이터·기대값·스크립트·실행 방식·Org·소스 변화는 새 버전·재승인 대상이다. 동작과 증거가 이미 있으면 그 사실을 바꾸지 않는다. 완료 시나리오 재실행은 새 run_id를 만든다.

사용자에게 코드 기반 기대값 초안이라는 점을 짧게 알리고 **`/testforce-ui` → 새로고침 → 계획**을 안내한다. 패널이 이미 열려 있으면 다시 여는 명령은 요청하지 않는다. **제목 클릭은 설명 열기, 체크는 실행할 시나리오 선택**임을 필요할 때 설명한다. 자연어 수정은 이 대화에서 받고, 큰 표를 직접 편집하려는 경우에만 고급 브라우저를 안내한다. 기본 승인 범위는 준비 후 도구 실행까지이며 준비까지만과 기존 데이터 예외 범위는 구분한다. 확인 체크 후 승인 버튼을 누르며 이름·날짜 입력은 없다. 같은 계획·범위에 유효한 승인이 있으면 반복 확인하지 않는다. 승인 뒤에는 **테스트 시작**을 누르도록 안내하며 Claude에게 실행을 다시 부탁하게 하지 않는다.

`status`에서 승인 상태를 읽을 수 있으나 **Mod bridge/action/token을 호출하거나 읽어 사용자 승인을 대신하지 않는다**. 브라우저 승인 요청, `reviewed: true`, TTY 키 입력도 대신 제출하지 않는다. 자연어 '좋아요'를 승인 파일로 변환하지 않는다. 사용자가 직접 패널/브라우저를 조작하거나 실제 터미널에서 대화해야 한다. 계획 JSON의 승인·시각·사용자 값을 만들어 넣지 않는다.
